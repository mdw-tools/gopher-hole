Attempt 4: Apple Containers + pi + LM Studio + hunk

Proposal · 2026-07-23 (rev 2: plain containers, current-directory-only mount) · gopher-hole work session

Background

gopher-hole is an exercise in operating isolated, safe coding agents. Three attempts precede this one:

AttemptIsolation layerVerdict
attempt-001-docker Docker container Works, but the audit found the firewall self-controlled (NET_ADMIN), the agent running as root, DNS wide open, and only a shared-kernel boundary.
attempt-002-lima Lima VM (vz + VirtioFS) Separate guest kernel, nftables allowlist a non-root agent can't touch, DNS via the host-agent only. Strongest local isolation so far.
attempt-003-cloud Disposable cloud VM (AWS/DO) Off-host entirely; rsync sync-back workflow. Strong isolation, but latency, cost, and cloud credentials in play.

Attempt 4 changes three things at once:

  1. Isolation layer: plain containers from Apple's open-source container tool. Its core design property is that every container runs in its own lightweight VM — a real hypervisor boundary with a separate guest kernel, unlike Docker's shared-kernel namespaces. This lands at attempt-001's ergonomics (image + run script + single project bind mount) with attempt-002's isolation properties, and directly fixes attempt-001's audited weaknesses: in-guest firewall rules live in a separate kernel, and the agent runs as a non-root user. This host runs macOS 26.5 with container CLI 1.1.0, so full networking is available.
  2. Harness + model: the pi coding agent talking to LM Studio running on the host at http://localhost:1234 (an OpenAI-compatible endpoint). This is a notable shift in the threat model: no API key ever enters the guest, and model traffic never leaves the container↔host boundary. The only internet egress an agent session needs is git and the Go module proxy.
  3. Review tool: hunk (a terminal diff TUI built specifically for reviewing agent-authored changesets) installed in the container alongside git.
Why not container machines? An earlier revision of this proposal used container machine (systemd-booted VMs with home-directory sharing). Verified against CLI 1.1.0: machines share the entire $HOME or nothing (--home-mount ro|rw|none) — there is no per-directory option — which would hand the agent your whole home directory, ~/.ssh included. Plain container run supports -v/--volume bind mounts of arbitrary single directories and offers the identical VM-per-container isolation. Machines' only other additions (systemd init, host-user mapping) aren't needed here: pi and hunk are ordinary processes. So: plain containers, sharing only the current project directory.

A note on sources: pi.dev is not fetchable from this environment, so all pi details below come from the GitHub monorepo (packages/coding-agent/README.md and docs/models.md), which documents install, provider configuration, and headless operation.

Architecture

Approach

Create attempt-004-apple-container/ following the shape of attempt-001 (image + launcher script) with attempt-002's documentation discipline, plus a smoke-test script standing in for unit tests, since this is infrastructure rather than application code:

FilePurpose
DockerfileContainer image: Ubuntu 24.04 plus git, curl, jq, python3, perl, Go 1.26, Node 22, @earendil-works/pi-coding-agent, hunkdiff; non-root agent user. No systemd — nothing here needs an init system.
entrypoint.shRuns setup-pi.sh (below) then execs the session command. In the optional hardening phase it grows a root stage that installs nftables rules before dropping to agent.

Makefileimage (build), verify (run verify.sh), clean (remove image + stray containers). Lifecycle is per-session via run.sh, so no start/stop targets are needed.
verify.shSmoke-test assertions per phase — the red/green driver for this work.
README.mdUsage, LM Studio setup, comparison to prior attempts, risks.

Container image

With no init system required, the image is a straightforward toolbox:

# Sketch — final version lands in attempt-004-apple-container/Dockerfile
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y \
      curl ca-certificates git jq ripgrep python3 perl iproute2 \
    && apt-get clean && rm -rf /var/lib/apt/lists/*
# iproute2: setup-pi.sh detects the host gateway with `ip route`
# (stock ubuntu:24.04 doesn't include it — spike finding)

# Go 1.26 from the official tarball (apt's golang is stale) — arm64, since
# containers on Apple Silicon run linux/arm64
ARG GO_VERSION=1.26  # pin the exact patch release at implementation time
RUN curl -fsSL "https://go.dev/dl/go${GO_VERSION}.linux-arm64.tar.gz" | tar -C /usr/local -xz
ENV PATH="/usr/local/go/bin:${PATH}"

# Node 22 (needed by pi and hunk), then the two npm tools
RUN curl -fsSL https://deb.nodesource.com/setup_22.x | bash - \
    && apt-get install -y nodejs \
    && npm install -g --ignore-scripts @earendil-works/pi-coding-agent hunkdiff

RUN useradd --create-home --shell /bin/bash agent
COPY entrypoint.sh setup-pi.sh /usr/local/bin/
USER agent
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["pi"]

On “maybe some of those come along for free”: on the ubuntu:24.04 OCI base, only perl-base is guaranteed (dpkg itself depends on it) — full perl and python3 are stripped from the minimized image, so both are installed explicitly (cheap and idempotent). Go is a different story: Ubuntu's apt archive ships a stale toolchain, so 1.26 comes from the official go.dev tarball, the same pattern attempt-003's cloud-init used.

Wiring pi to LM Studio

pi reads custom providers from models.json under its agent dir (~/.pi/agent/). LM Studio speaks the OpenAI completions API, so the config is (per pi-mono/docs/models.md):

{
  "providers": {
    "lmstudio": {
      "baseUrl": "http://192.168.64.1:1234/v1",
      "api": "openai-completions",
      "apiKey": "lmstudio",
      "models": [
        { "id": "<model-id-from-/v1/models>", "contextWindow": 128000, "maxTokens": 32000 }
      ]
    }
  }
}

Two guest-specific details, both handled by setup-pi.sh at container start:

  • “localhost” means the host, from outside. Inside the container, the host is reached via the vmnet gateway. Rather than hardcoding 192.168.64.1, detect it: ip route | awk '/default/ {print $3}'.
  • Model list comes from LM Studio itself. curl http://$GW:1234/v1/models returns the loaded models; the script generates one models.json entry per model so pi's --model flag matches whatever is actually loaded.

On the host side, LM Studio must serve on the network interface the vmnet bridge can reach — its server defaults to loopback only. That's the “Serve on Local Network” toggle in the LM Studio server settings (or the equivalent lms server flag).

Session workflow

# one-time
make image

# each session — disposable container, only the project dir shared
./run.sh ~/code/src/github.com/some/project        # drops to bash in that dir
./run.sh ~/code/src/github.com/some/project pi     # or launch pi directly

# under the hood, run.sh does roughly:
container run --rm -it \
  --volume "$PROJECT_DIR:$PROJECT_DIR" \
  --volume "$HOME/.pi-gopher-hole:/home/agent/.pi" \
  --workdir "$PROJECT_DIR" \
  --env GIT_AUTHOR_NAME=... --env GIT_AUTHOR_EMAIL=... \
  gopher-hole "$@"

# review the agent's changes — either side of the boundary works,
# since the code tree is the same files:
./run.sh ~/code/src/github.com/some/project hunk diff   # in-container TUI
# ...or hunk/git/IDE on the host

Because the project directory is mounted at its host absolute path, hunk, git, and your IDE agree about file locations on both sides of the boundary. With no ~/.ssh or ~/.gitconfig in the container, git authentication deliberately stays on the host: the agent works and commits locally (identity forwarded via GIT_AUTHOR_*/GIT_COMMITTER_* env vars from host git config), and you push from the host after review — the same review-then-push discipline attempt-003 used.

Decision points

1. Plain containers instead of container machines (decided 2026-07-23)

Machines share all of $HOME or nothing (verified: CLI 1.1.0 offers only --home-mount ro|rw|none); plain container run supports arbitrary -v bind mounts with identical VM-per-container isolation. Decision: plain containers, mounting only the current project directory. This also removes the systemd requirement and the whole-home exposure concern from the earlier revision.

2. Session lifecycle: disposable per-session vs long-lived container (confirmed 2026-07-23: --rm per session)

A long-lived container with container exec would let several sessions share one guest, but keeps state you'd rather not accumulate. With --rm, every session gets a pristine guest, and the only state that survives is what's in the two mounts (project dir, pi state) — which is exactly the state we want to survive.

Recommendation: --rm per session. Concurrent sessions on different projects are simply concurrent run.sh invocations, each in its own VM. Startup cost is expected to be sub-second-to-seconds (spike confirms).

3. Where pi state lives (confirmed 2026-07-23: dedicated mounted dir)

With no home share, pi's default ~/.pi/agent/ is container-local and would vanish with each --rm. Sessions and provider config are worth keeping.

Recommendation: mount a dedicated host dir: -v ~/.pi-gopher-hole:/home/agent/.pi. pi state persists across disposable containers, is inspectable from the host, and never collides with any host-side ~/.pi.

4. Egress hardening — in or out of scope?

With the model local, the container needs very little internet: git (github.com:443) plus Go module downloads cover a working session; npm/apt egress happens only at image-build time. go get / go mod download default to the module proxy, so the allowlist needs proxy.golang.org and sum.golang.org (checksum verification), plus storage.googleapis.com which backs the mirror — the same trio attempt-002 allowlisted. Modules that opt out of the proxy fall back to direct VCS: the github allowance covers those, and bitbucket.org:443 is added for go get of Bitbucket-hosted modules. That keeps the full list small (gateway:1234; github.com, bitbucket.org, and the Go module proxy on 443) — and because each container is its own VM with the agent as a non-root user, the rules are actually trustworthy (unlike attempt-001).

Note for private Bitbucket modules: those require GOPRIVATE=bitbucket.org/... (skip proxy and checksum db) and read credentials in the guest, which intersects with the no-credentials decision below — the documented escape hatch is a read-only app password or deploy key scoped to fetch, supplied per-session as an env var, never baked into the image.

Recommendation: include it as an explicitly optional final phase (Phase 6). MVP first; don't block the workflow validation on firewall plumbing. The entrypoint gains a root stage (set rules, then drop to agent via setpriv) — attempt-001's pattern, now effective.

Trade-offs and open questions

ItemAssessment
Guest→host reachability Resolved by spike (2026-07-23). The vmnet gateway (192.168.64.1) routes to the host: with LM Studio's “Serve on Local Network” enabled, the guest retrieves the model list from http://$GW:1234. With loopback-only binding the connection is refused, confirming the toggle is load-bearing.
Bind-mount ownership (uid/gid) Resolved by spike (2026-07-23). virtiofs maps ownership transparently in both directions: host files appear owned by the running container user (verified at uid 0 and uid 1000), and guest-created files land on the host owned by the host user. No uid-matching workaround needed.
LM Studio LAN exposure Serving on non-loopback means other devices on the LAN can reach the model server. Mitigation options: macOS application firewall, or restricting LM Studio to the vmnet subnet if it supports interface binding. Documented in the README; acceptable for a dev machine on a trusted network.
No credentials in the guest Deliberate: no ~/.ssh, no ~/.gitconfig, no API keys. The cost is that git push/pull against remotes happens on the host, not in-session. That matches the repo's review-then-push philosophy; if in-guest fetch becomes annoying (e.g. go get of private Bitbucket modules), a read-only deploy key or app password supplied per-session is the escape hatch (documented, not built).
Local model capability pi's usefulness depends on the loaded model's tool-calling quality. That's an LM Studio-side choice, out of this repo's scope, but the smoke test (Phase 3) uses a trivially verifiable prompt so harness problems aren't confused with model problems.
Feature maturity apple/container is a young tool; CLI flags may shift between releases. Every container invocation lives in run.sh/Makefile, so adaptation is localized. CLI 1.1.0's flag set for run (-v, --mount, -w, -e, -u, --rm, -d) was verified directly on 2026-07-23.
TUI over container run -it hunk and interactive pi need a proper TTY. Expected to work; confirmed in the spike.
Git hook / build-script poisoning Same residual risks as every prior attempt with a shared tree: .git/hooks written in the guest execute if git runs on the host, and poisoned Makefiles execute wherever they're run. Host-side core.hooksPath mitigation carries over from attempt-002's README.

Implementation checklist

Infrastructure work rather than application code, so the red/green cycle runs through verify.sh: each phase first adds a failing assertion (RED), then the piece that makes it pass (GREEN). Phase 0 is a manual spike — its findings can amend this proposal before anything is built. (CLI presence, version 1.1.0, and the flag sets for machine create and run were already verified during proposal drafting.)

Phase 0 — Spike: validate the load-bearing assumptions

  • container system start succeeds; container run --rm -it ubuntu:24.04 bash gives an interactive shell with a working TTY (arrow keys, full-screen apps). Result: apiserver responds (though system status misreports launchd state under the sandboxed shell); guest kernel 6.18.15 confirms VM-per-container; -t allocates /dev/pts/0. Full-screen interactivity gets implicit validation at first real session.
  • Bind-mount check: container run --rm -it -v "$PWD:$PWD" -w "$PWD" ubuntu:24.04 bash — files visible both directions, live; note the uid/gid of guest-created files as seen from the host, and of host files as seen from the guest. Result: bidirectional visibility confirmed; virtiofs maps ownership transparently — host files appear owned by the container user (tested uid 0 and uid 1000), guest-created files land on the host owned by the host user (501). No uid-matching workaround needed.
  • On the host: start the LM Studio server on :1234 with “Serve on Local Network” enabled. Result: done; with loopback-only binding the guest got connection-refused, confirming the toggle is required.
  • In the guest: GW=$(ip route | awk '/default/ {print $3}'), then curl http://$GW:1234/v1/models returns the model list. This is the go/no-go check for the whole approach. Result: PASS — gateway 192.168.64.1 serves the model list. Note: stock ubuntu:24.04 lacks iproute2; the gateway is parsed from /proc/net/route or iproute2 gets installed in our image (it is).
  • Measure cold container startup time (--rm lifecycle viability). Result: ~0.6s wall-clock for container run --rm ubuntu:24.04 true with the image cached — disposable per-session containers are effectively free.
  • Record findings; amend this proposal if anything failed (especially uid mapping → may add a --uid/build-arg fix to Phase 1). Result: all checks passed; both open-question rows above are resolved; the only amendment is adding iproute2 to the image.

  • RED Add verify_firewall: in-guest curl https://example.com fails; curl http://$GW:1234/v1/models, git ls-remote https://github.com/..., git ls-remote https://bitbucket.org/...
